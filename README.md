# GC Stats Widgets

Front of the GC Stats broadcast widgets (OBS Browser Source, embeds). Each widget fetches its data from a public GC Stats endpoint and renders it. No backend, no database: a static site.

Built to be forked: change the UI, deploy it with your own design.

## How it works

```
Browser Source  ->  /head-to-head?team_a=1&team_b=2   (this repo, static)
                        |
                        v  fetch, same query string
                    GC Stats  /api/widgets/head-to-head   (JSON, public, CORS)
```

| Widget | Page | Data endpoint |
| --- | --- | --- |
| Head to Head (radar) | `/head-to-head` | `/api/widgets/head-to-head` |
| Heatmap | `/heatmap` | `/api/widgets/heatmap` |
| Live map veto | `/veto?match_id=123` | `/api/widgets/veto` |

The query string of the page is forwarded as is to the endpoint, so the filters are the ones GC Stats documents (`team_a`, `team_b`, `tournament_id`, `patch`, `mappool`, `map`, `side`, `color`, ...). Links are generated by the builder on the GC Stats `/widget` page.

Extra params handled by this front only:

- `credit=1` shows the small "Widget provided by GC Stats" line (off by default, opt in).
- `lang=fr` forces the language (browser language otherwise, English as fallback).
- `rotation=atk` or `rotation=def` (heatmap only) turns the map to the attackers or defenders point of view (`atk` by default).
- `refresh=30` re-fetches the data every 30 seconds (min 10, off by default; a failed refresh keeps the last data). The veto widget is live: it refreshes every 2 seconds by default (min 1).

`credit`, `lang`, `refresh` and `rotation` are not forwarded to the API.

## Run

```bash
npm install
cp .env.example .env     # VITE_GCS_API_URL = the GC Stats site
npm run dev
npm run build            # static output in dist/
npm test                 # unit tests (vitest)
```

### Deploy (Docker + nginx)

The `Dockerfile` builds the site and serves `dist/` with nginx (unprivileged, port 8080). Every path falls back to `index.html`, query strings are untouched.

- `GCS_API_URL` (container environment, required): base URL of the GC Stats site. It is read at start and served as `/config.js`, so the same image runs in staging and production. `VITE_GCS_API_URL` is only the fallback of `npm run dev` and of a plain static host.
- The `Image` workflow (push on `main`) tests, builds, scans (Trivy) and pushes `ghcr.io/osthelia/osthelia-widgets:<sha>`, then bumps the staging tag in the GitOps repository (secret `GITOPS_DEPLOY_KEY`).

```bash
docker build -t osthelia-widgets .
docker run --rm -p 8080:8080 -e GCS_API_URL=https://gc-stats.app osthelia-widgets
```

### Anywhere else

Deploy `dist/` on any static host, with every path falling back to `index.html`, and set `VITE_GCS_API_URL` at build time.

On the GC Stats side, set `NEXT_PUBLIC_WIDGETS_URL` to the URL where you host this front, so the builder generates links to it.

## Restyle

- `src/theme.css`: colors, font, credit style (CSS variables).
- `src/widgets/<name>/`: component and CSS of one widget.
- `src/widgets/registry.ts`: add a widget by creating its folder and one line here.
- `src/useWidgetData.ts`: the fetch, shared by all widgets.
